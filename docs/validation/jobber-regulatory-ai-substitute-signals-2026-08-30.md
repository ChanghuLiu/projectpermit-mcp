# Jobber regulatory-AI substitute signals — 2026-08-30

## Purpose

Record independent public evidence that real contractors are already using AI / custom software for municipality-specific permit, code and regulatory work inside estimating / field-service workflows.

This evidence is strategically important for two opposite reasons:

1. it independently validates that the workflow exists and costs real contractor time;
2. it proves that generic AI / custom GPTs are already a substitute, so ProjectPermit cannot win merely by offering another chat/search interface.

This is **public qualitative evidence only**. It is not a recent bounded denominator, buyer commitment, usage of ProjectPermit or payment. No E2/E3/E4/E5 increase.

## Signal 1 — BC fire-protection contractor uses AI extensively for changing municipal codes

A current Jobber Home Service Community discussion on AI usage includes a British Columbia fire-protection contractor who says they use AI extensively for:

- code research;
- deficiency solutions;
- finding current replacements for expired/outdated devices;
- identifying the latest requirements;
- researching codes that change over time and differ across municipalities.

The contractor explicitly says this has saved **hours** that would otherwise be difficult to execute manually.

Public source:
- https://community.getjobber.com/discussions/contruction-and-home-improvement/how-are-you-using-ai-in-your-day-to-day-operations/12973

### What this supports

- maintained/current regulatory information is a real recurring operational problem, not a hypothetical software-founder pain point;
- cross-municipality differences matter to real field-service companies;
- contractors are already willing to put AI into the workflow when it reduces research burden;
- time savings can be large enough for the contractor to describe them in hours.

### What it does NOT support

- number of checks/month;
- willingness to pay for ProjectPermit;
- preference for external API vs ChatGPT/custom GPT;
- suitability of ProjectPermit's current residential-renovation family set for fire-protection work.

No E-level increase.

### Why this verified identity matters

This is a materially stronger build-vs-buy benchmark than an anonymous statement.

It demonstrates a real contractor with all of the following:

- Vancouver / Lower Mainland jurisdiction exposure;
- Jobber as a production workflow system;
- owner-level estimating involvement;
- substantial automation capability;
- repeated estimating activity;
- willingness and ability to build a municipality-specific permit calculator and code GPT internally.

That is almost the strongest possible falsification of a weak ProjectPermit thesis.

A product whose value is only:

`city -> permit price / code search -> AI answer`

is directly vulnerable to a technically capable contractor building the workflow themselves.

### Strategic consequence

A winning external product must provide value that is harder to maintain than a small custom GPT or calculator:

- authoritative first-party evidence;
- explicit source verification / freshness;
- change detection;
- deterministic fact schema instead of conversational answers;
- conservative unknown/missing states;
- multi-jurisdiction normalization;
- work-record / quote consequence;
- integration / idempotency;
- source-rights / licensed-content handling where needed.

This strengthens the importance of the existing evidence/freshness/source-observability moat.

### Future electrical-adjacent interpretation

Do **not** broaden ProjectPermit into electrical now.

If electrical is later validated as a market, Vancity Electric suggests a more realistic product shape:

`existing contractor DIY tool / Jobber / Zapier -> ProjectPermit maintained evidence/currentness API -> contractor keeps internal estimation/judgement UI`

In other words, the best buyer may not want ProjectPermit to replace their estimator GPT. They may want a maintained authoritative layer underneath it.

That is a much more defensible API/MCP role.

## Signal 3 — permits already belong inside the estimate cost model

A Jobber quoting discussion requests a richer estimate catalog and explicitly lists **permits** alongside materials, labor and subcontractors as items needed to complete a job.

The poster says estimates are currently built outside Jobber until the prices are known, then recreated in Jobber for the customer.

Public source:
- https://community.getjobber.com/discussions/quoting/we-need-a-catalog-to-build-estimates-%F0%9F%93%97/2416

### Interpretation

This is strong workflow-placement evidence:

- permit-related facts/costs are part of quote construction, not necessarily a downstream filing-only concern;
- information can be assembled outside the field-service system and then manually transferred into the quote;
- an embedded regulatory result can create value before any permit application automation exists.

It does not prove that the same user needs jurisdiction research or would pay for ProjectPermit.

## Combined interpretation

These signals independently support three parts of the Layer-C thesis:

### 1. Workflow reality

Contractors actually perform municipality/code/permit research and integrate its consequences into pricing or operational decisions.

### 2. Existing AI adoption

AI is already being used for code research and estimating. The future competitor is not only permit SaaS — it is also `ChatGPT + PDFs + custom GPT + contractor knowledge`.

### 3. Differentiation requirement

Therefore ProjectPermit's commercial wedge cannot be:

> `Ask AI a permit/code question.`

That is already cheap and DIY-able.

The candidate externalized capability is instead:

> `project/work-record facts -> deterministic current requirement/obligation result -> official evidence + freshness/change identity -> bounded quote/scope/schedule consequence`

## Buyer archetype consequence

The existing first buyer target remains a high-fit residential remodel/design-build contractor because it matches current ProjectPermit coverage and does not require a new vertical before validation.

However, these public signals create a **post-validation high-pain adjacent pool**:

- fire-protection contractors;
- electrical contractors;
- solar contractors;
- other multi-jurisdiction specialty trades where code/permit updates are frequent and explicitly embedded in estimating/service decisions.

Do **not** broaden the product into these trades now. Their evidence should influence future ranking only after the current Layer-C buyer gate is crossed.

## Build-vs-buy consequence

The verified Vancity Electric example is a direct warning:

- sophisticated contractor + narrow local need -> can build internally;
- external service must reduce maintenance/risk, not merely initial development effort.

A buyer who says `I can build a permit calculator/GPT once and maintain it myself` is weak commercial evidence.

A buyer who says `I already built something, but keeping current across municipalities/codes is the painful part` would be high-value evidence for ProjectPermit's maintained layer.

The Vancity example also suggests a third commercial possibility:

- buyer keeps its own UI / estimator GPT;
- ProjectPermit becomes the maintained source-of-truth API under that internal tool.

This is structurally compatible with MCP/API distribution and may be more attractive to technically capable businesses than replacing their existing workflow.

## Updated E2 question

For buyers already using AI/custom tools, add this question after the `last 20 estimates` denominator:

> If you already use ChatGPT/custom GPTs/spreadsheets for this, what part still requires manual checking or makes you distrust the result — source currency, municipal differences, official citations, code updates, missing facts, or writing the result back into the quote/job?

Then ask:

> If that maintenance/currentness layer were handled externally, would you keep your existing DIY tool and call the maintained API, replace the DIY tool, or still maintain everything internally?

This directly tests the ProjectPermit moat rather than generic AI interest.

## Decision

No product build or pricing change.

No E-level increase.

The evidence does strengthen one strategic conclusion:

> **ProjectPermit's moat thesis is now more specifically `maintenance + evidence + deterministic workflow consequence`, not AI retrieval.**
